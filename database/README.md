# Database contents

supabase/migrations/ is the authoritative, ordered installation and update history (25 files). FRESH-INSTALL.sql is a convenience concatenation for a NEW Supabase project only; choose it OR the CLI method in docs/DEPLOY.md.

The schema includes panda_accounts, panda_records, panda_events, private helper functions, RLS, validated/atomic save RPCs, private chat support and the client intake questionnaire (record kind client_intake, migration 023) the client archive date (migration 024) and the coach's status-only intake rule (migration 025). Content seeds include recipes, exercise catalogue references, education/training articles, food references and plan templates. User identities refer to Supabase Auth. Accounts/private customer records are intentionally absent; the owner creates the coach and clients in the new project.

This is not a dump of the previous live database. Auth settings and Function allowed origins must be set as documented. No existing production customer data or private uploads are supplied.

Client intake (migration 023): one client_intake record per client (id = owner = the client's auth uuid), readable by the coach and that client only, with no package feature required. Clients write it while onboarding or after the coach reopens it; submitting locks it. The database stamps submitted_at, submitted_profile (name, sex, age, height, weight and goal copied from the clients record at submission) and health_flag. Saves that include an intake are logged in panda_events with the fixed label "Updated intake questionnaire". Migration 023 patches the installed panda_save and readable() in place and stops if the 009, 010 or 014 changes are missing; never re-create those functions from an older file.

Intake retention: settings/brand.intake_retention_months is how many whole months (1–120) a client's intake is kept after the client is archived; migration 023 sets it to 24 (2 years) when absent. Empty or null means no automatic deletion. panda_private.intake_retention_months() returns the configured value. No deletion job exists yet, so nothing is deleted automatically today.

Client archive date (migration 024): the clients record carries data.archived_at, an ISO timestamp, only while status is 'archived'. A trigger (panda_private.stamp_client_archive) sets it when a client is archived, keeps the first date while the client stays archived, and removes it when the client gets any other status; archiving again records a new date. It is server-set only: values sent by the coach, the client or a direct write are discarded, and panda_save already refuses client edits outside their personal fields. Clients who were already archived when 024 was applied are stamped with the upgrade time, so their retention period starts then. A future deletion job can select intakes whose client has archived_at older than intake_retention_months.

Coach intake rule (migration 025): the coach may only change an intake's status. On an existing intake the record must be sent unchanged except for status, which may stay the same or become 'reopened'; for a client with no intake the coach may create one only as 'reopened' with the empty skeleton. Changed answers, submitted_at, submitted_profile or health_flag are refused with a message naming what cannot change (leaving the server fields out is allowed). Clients, the service role and direct writes are unaffected. 025 patches guard_client_intake() in place: if migration 023 is ever re-run, re-run 025 afterwards, because 023 re-creates that function without the patch. The portal's backup restore never changes intakes.
